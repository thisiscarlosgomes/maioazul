# V1.1 public data layer

V1.1 remains at **/api/v1**. There is no parallel /api/v1.1 namespace. Existing endpoints, feature IDs, original memberships, source attributes, GeoJSON and six legacy dataset payloads remain compatible. New fields and catalog entries are additive. No authentication or writes are introduced. ETags, CORS, revision tracking and HEAD/OPTIONS remain shared across routes.

## Geography and places

Nine collections are added: admin-boundaries, localities, schools, health, government, heritage, land-use, waste-infrastructure and connectivity. Classification uses explicit source tags/categories; names and narrative descriptions do not generate facilities. Empty new domains are planned. Existing empty water-points remains no-records. Availability is distinct from a sports asset's lifecycleStatus=planned. OSM and editorial records are not automatically official government records; their provenance and licenses remain attached through source IDs.

`GET /places?q=calheta&limit=10` returns stable locality entities. `GET /places/calheta` links to `/features`, `/infrastructure` and `/datasets` beneath that place URL. All list endpoints support limit 1–500 (default 100), offset (default 0), counts, revision and next/previous links.

Places are pinned in `data/place-registry.json`. IDs do not regenerate when a name changes. Explicitly reconciled source IDs refer to the same entity; grouped source localities remain locality-group entities rather than invented individual settlements. The first defining feature supplies representative geometry. No administrative boundary, nearest-village association or duplicate-facility resolution is implied.

Place feature and infrastructure listings accept the existing feature filters. Infrastructure includes the public-infrastructure, schools, health, government, water-points, waste-infrastructure, connectivity, sports and transport collections. Associations include a source-based explanation. Dataset links require an explicit dataset placeId association or a normalized record's placeId. Calheta currently has source locality and school records, but no linked statistical series. An empty list is incomplete coverage, not evidence of no services. Consult the global dataset catalog for island/national context.

## Dataset support

The catalog adds population, households, housing, employment, education, health, water, waste, biodiversity, connectivity, business-demography, municipal-finance, municipal-budget and public-procurement.

Municipal-budget contains public 2025/2026 budget-summary extractions. These have **needs_review** quality and retain source caveats. They are approved-budget amounts, not expenditure execution or procurement. Only numeric source summary fields ending in `_cve` are imported; no totals are estimated and no workstation paths or unrelated extraction tables are published. Population additionally exposes the existing dashboard island-level record with needs_review quality and an explicit unverified-publication caveat. The remaining new datasets are planned pending a structured source adapter. Narrative population mentions and database-backed dashboard routes are not treated as validated statistical extracts.

`GET /datasets/{id}` preserves legacy source payloads. Planned datasets return `payload:null`, explicit status, empty sourceIds and caveats. `GET /datasets/{id}/records` provides paginated normalized indicators. This additive endpoint is currently populated for municipal-budget and dashboard population. Legacy datasets remain available through their original payloads while their normalized record endpoints are explicitly planned.

Example:

```text
/api/v1/datasets/municipal-budget/records?year=2026&indicator=revenue_total_cve
```

Records carry stable id, year, geographicScope, locality, placeId, indicator, value, unit, sourceId, sourceRecordId, referencePeriod, updatedAt, retrievedAt, quality and caveats. Unknown timestamps or locality are null. Monetary units are CVE. Updated dates are source publication dates, never claimed as retrieval dates. Source manifests retain checksums and licenses; unspecified reuse rights remain unspecified.

Filters: year, geographicScope, locality, placeId, indicator, sourceId and referencePeriod use exact matches and combine with AND. Unknown placeId is 404; a known place without rows returns an empty list. No island-wide totals are allocated to localities. Dataset status describes source availability; recordsStatus describes normalized adapter availability. A filter matching no observations does not turn an available dataset into a planned one.

## Transport domain

`GET /transport` advertises `/routes`, `/schedules`, `/arrivals`, `/departures`. All four currently return status=planned, empty arrays, null timestamps and a no-feed caveat. Historical transport statistics and mapped port/airport features remain available at their original routes.

OpenAPI defines route, endpoint, operator and schedule contracts: air/maritime mode, origin/destination, optional source codes and geographic references, operator, service number, service date, source timezone, scheduled and actual departure/arrival, normalized/source status and provenance. Actual times remain null until observed. These are capability definitions, not synthetic records. List filters accept mode, origin, destination, operatorId and date, plus pagination; invalid values are rejected even on empty feeds.

## Compatibility and validation

The test suite retains a V1 baseline of feature IDs/memberships and dataset payload checksums. It also verifies source-value equality, linked-place resolution, pagination, planned states, invalid queries, schemas, CORS, conditional GET and HEAD. Revision hashing now includes the complete dataset and place metadata, so changes to associations or plans invalidate the snapshot revision. Public read-only source sync remains deterministic and never writes to source applications.

The OpenAPI document describes the implemented API, not OGC/DCAT certification. Stronger catalog interoperability and reviewed source adapters remain separate future work.
